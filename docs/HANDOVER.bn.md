# Iconic Online — ক্লায়েন্ট হ্যান্ডওভার

**ক্লায়েন্টকে অ্যাপের অ্যাকাউন্ট দিন, সোর্স বা হোস্টিং অ্যাক্সেস নয়।** Git রিপোজিটরি, ডেপ্লয়মেন্ট ও সার্ভারের নিয়ন্ত্রণ আপনার কাছে রাখুন। ক্লায়েন্টের কাজের জন্য যতটুকু দরকার ততটুকু অ্যাপ-পারমিশন দিন, কিন্তু Git, SSH/SFTP, cPanel/CyberPanel, ফাইল ম্যানেজার বা ডেটাবেসের অ্যাক্সেস দেবেন না। কোডের মালিক হবে ডেপ্লয়মেন্ট অ্যাকাউন্ট; ওয়েব সার্ভার ও PHP শুধু কোড পড়বে, লিখবে না।

এই ব্রাঞ্চ **owner-only staging**-এর জন্য। এটি এনকোডেড প্যাকেজ নয় এবং ক্লায়েন্টের লাইভ সার্ভারে দেওয়ার মতো পূর্ণ নিরাপত্তা যাচাই হয়নি।

## কী বাদ গেছে

- পুরোনো আপলোড করা ছবি, PDF, পেমেন্ট ফাইল ও সার্ভার লগ; এগুলো রিপোজিটরির অ্যাসেট নয়। হোস্টিং বা ডেটাবেস থেকে কিছু মোছা হয়নি। পুরোনো রেকর্ডে এসব ফাইলের লিংক থাকলে অনুমোদিত ব্যাকআপ থেকে আলাদা ডেটা মাইগ্রেশন লাগবে।
- ডিফল্ট হোস্টিং পেজ, অব্যবহৃত ব্যাকআপ ও টেস্ট পেজ, পুরোনো পেমেন্ট ডেমো ও অযাচাইকৃত ওয়েবহুক। বর্তমান ম্যানুয়াল রিচার্জ পেজ রাখা হয়েছে; নম্বর `payment_settings`-এ না থাকলে পুরোনো নম্বরে টাকা পাঠাতে বলবে না।
- প্রোফাইলে ক্যামেরা ও লোকেশন সংগ্রহ, ব্যক্তিগত তথ্য/ছবি অন্যত্র পাঠানো, এবং কিছু সার্ভার/অর্ডার নোটিফিকেশন। ব্যবহারকারী নিজে বাছাই করলে প্রোফাইল ছবি শুধু এই সার্ভারেই সেভ হয়।
- সোর্সে থাকা ডেটাবেস/পেমেন্ট কনফিগ এবং কিছু পুরোনো API key। সংশ্লিষ্ট NID, TIN, জন্মনিবন্ধন ও ফোন-তথ্যের চারটি অযাচাইকৃত lookup endpoint বন্ধ (`410 Gone`)। সংশ্লিষ্ট UI পুরোপুরি সরানো হয়নি; পুরোনো লিংক থেকে সেবাটি এখন ব্যবহার করা যাবে না।

**Git ইতিহাসে পুরোনো ডেটা ও সিক্রেট থাকতে পারে।** বর্তমান ব্রাঞ্চ থেকে ফাইল সরানো মানে ইতিহাস থেকে মুছে যাওয়া নয়। রিপোজিটরি ব্যক্তিগত রাখুন; `.git`, পুরোনো ZIP বা লাইভ DB dump শেয়ার করবেন না। পুরোনো DB/API/পেমেন্ট/বট কী প্রত্যাহার বা ঘোরান এবং পুরোনো অ্যাডমিন টোকেন ও সেশন বাতিল করুন। সাইটটি আগে লাইভ থাকলে সংশ্লিষ্ট লগ ও ডেটা অ্যাক্সেস পর্যালোচনা করুন।

## নিজের হোস্টে ব্যক্তিগত স্টেজিং

`deploy/nginx-staging.conf.example` ও `deploy/php-fpm-staging.conf.example` **Nginx + PHP-FPM**-এর নমুনা। নিজের TLS, PHP-FPM socket এবং অনুমোদিত IP/VPN দিয়ে সেট করুন। অন্য web server বা CyberPanel ব্যবহার করলে সমতুল্য নিয়ম আলাদাভাবে বসিয়ে পরীক্ষা করুন; শুধু রিপোর ফাইল আপলোড করলে নিয়মগুলো সক্রিয় হয় না। স্টেজিং ইন্টারনেটে খুলবেন না।

1. রিভিউ করে ব্রাঞ্চের ক্লিনআপ কমিট করার পর `python3 tests/check_handover.py HEAD --php php` চালান (PHP 8.3+ CLI)। এরপর **নিজের ডেপ্লয়মেন্টের জন্য** সোর্স এক্সপোর্ট করুন:

   ```sh
   umask 077
   git -c tar.umask=0027 archive --format=tar.gz --output=/private/iconiconline-staging.tar.gz HEAD
   ```

   `/private`-এর বদলে আপনার সুরক্ষিত, ওয়েবরুটের বাইরের ডিরেক্টরি দিন। `git archive` কমিটের ফাইল নেয়; uncommitted পরিবর্তন এতে যায় না। `.gitattributes` ডেভেলপমেন্ট ফাইল, SQL, লগ, আপলোড ও লোকাল কনফিগ বাদ রাখে। আর্কাইভে PHP সোর্স আছে—ক্লায়েন্টকে পাঠাবেন না।
2. নতুন `/srv/iconiconline/staging/web` ডিরেক্টরিতে এক্সপোর্ট খুলুন (পুরোনো webroot বা Git চেকআউটের ওপর নয়)। নমুনা কনফিগে `iconic-staging` আলাদা PHP-FPM সার্ভিস ইউজার, `www-data` ওয়েব সার্ভিস গ্রুপ। নিচের কমান্ডগুলো **নিজের স্টেজিং হোস্টে**, সার্ভিস ইউজার বানানোর পর চালাবেন:

   ```sh
   web=/srv/iconiconline/staging/web
   sudo install -d -o root -g www-data -m 0750 /srv/iconiconline/staging "$web"
   sudo tar -xzf /private/iconiconline-staging.tar.gz --no-same-owner -C "$web"
   sudo chown -R root:www-data "$web"
   sudo find "$web" -type d -exec chmod 0550 {} +
   sudo find "$web" -type f -exec chmod 0440 {} +
   sudo install -d -o root -g www-data -m 0550 "$web/uploads"
   sudo install -d -o iconic-staging -g www-data -m 0750 "$web/uploads/avatars"
   sudo install -d -o iconic-staging -g www-data -m 0700 /srv/iconiconline/staging/sessions
   sudo -u iconic-staging test ! -w "$web/index.php"
   sudo -u iconic-staging test ! -w "$web"
   sudo -u iconic-staging test -w "$web/uploads/avatars"
   ```

   কোড নয়, স্টেজিংয়ে শুধু `uploads/avatars` ও ওয়েবরুটের বাইরের session directory PHP-কে লিখতে দিন। পরিচয়পত্র, অর্ডার ফাইল, পেমেন্ট ছবি বা অন্য ব্যক্তিগত আপলোডের path সরাসরি ওয়েব থেকে খোলা যাবে না। এই কারণে পুরোনো ফাইল-আপলোড/ডাউনলোডের ফ্লো এই স্টেজিং কনফিগে ইচ্ছাকৃতভাবে চালু নয়।
3. PHP-FPM পুল কনফিগ ওয়েবরুটের বাইরে `0600` পারমিশনে ইনস্টল করুন। `ICONIC_DB_HOST`, `ICONIC_DB_NAME`, `ICONIC_DB_USER`, `ICONIC_DB_PASSWORD` এবং প্রয়োজন হলে `ICONIC_DB_PORT` (ডিফল্ট `3306`) সেট করুন। পুরোনো সিক্রেট বা লাইভ ডেটা ব্যবহার করবেন না। MySQL/MariaDB, PHP-এর `mysqli`/`mysqlnd` ও `pdo_mysql` লাগবে। পূর্ণ DB schema এই রিপোতে নেই; `deploy/sql/deposit_requests.sql` শুধু একটি schema fragment। অনুমোদিত schema ও কৃত্রিম টেস্ট ডেটা ব্যবহার করুন।
4. Nginx ও PHP-FPM কনফিগ যাচাই করে রিলোড দিন। অনুমোদিত ও অননুমোদিত দুই নেটওয়ার্ক থেকে পরীক্ষা করুন। বাইরের নেটওয়ার্কে `/`, `/admin/` ও PHP পেজ বন্ধ থাকবে। অনুমোদিত নেটওয়ার্কেও `/.git/HEAD`, `/config.json`, `/includes/configuration.php`, `/pdf/...` ও `/uploads/...php` পাওয়া যাবে না। স্বাভাবিক লগইন, ছবি বাছাই করে আপলোড এবং ম্যানুয়াল রিচার্জ টেস্ট ডেটা দিয়ে আলাদাভাবে যাচাই করুন। টেস্টে বাস্তব পরিচয়পত্র/পেমেন্ট পাঠাবেন না।

## লাইভ করার আগে

- আলাদা ক্লায়েন্ট ভূমিকা ও অ্যাডমিন রুটের অথরাইজেশন, CSRF, পুরোনো MD5 পাসওয়ার্ডের মাইগ্রেশন/রিসেট এবং লগইন rate limit যাচাই করুন। কয়েকটি সংবেদনশীল অ্যাডমিন endpoint-এ সেশন চেক যোগ হয়েছে, কিন্তু পুরো অ্যাডমিন প্যানেল অডিট হয়নি।
- DB schema, পেমেন্ট মালিকানা/সেটিংস, পুরোনো রেকর্ড ও ফাইলের মাইগ্রেশন, এবং ব্যক্তিগত ফাইলের অনুমোদন-পরীক্ষিত ডাউনলোড যাচাই করুন। সরাসরি পাবলিক ফাইল লিংক চালু করে এই ধাপ এড়িয়ে যাবেন না।
- পরিচয়পত্র/জন্মনিবন্ধন, ফোন/লোকেশন/বায়োমেট্রিক ডেটা বা বাইরের API-র ফিচার অনুমতি ও ডেটা ব্যবহারের নিয়ম যাচাই ছাড়া হস্তান্তর বা চালু করবেন না। অপরীক্ষিত outbound সংযোগ স্টেজিংয়েও বন্ধ রাখুন।

## PHP এনকোডিংয়ের সীমা

Base64, minification বা ZIP ফাইল এডিট আটকায় না। ক্লায়েন্টের হোস্টে দিতেই হলে **পর্যালোচিত PHP**-এর জন্য লাইসেন্সড ionCube Encoder এবং টার্গেট PHP সংস্করণের সঙ্গে সামঞ্জস্যপূর্ণ ionCube Loader বিবেচনা করা যায়। এখানে সেই encoder বা টার্গেট হোস্টের তথ্য নেই, তাই কোনো ফাইলকে এনকোডেড বলা হচ্ছে না। ক্লায়েন্ট সার্ভারের মালিক হলে সে এনকোডেড ফাইলও বদলে বা সরিয়ে নিজের কপি চালাতে পারে। HTML, CSS ও JavaScript ব্রাউজারে দেখা/লোকালি বদলানো যায়; সার্ভারের কোড বা ডেটা বদলানোর অনুমতি আলাদাভাবে নিয়ন্ত্রণ করতে হবে।

ক্লায়েন্টের হোস্টের জন্য ডেটাবেস বাদ দিয়ে আলাদা ZIP বানানোর ধাপ: [এনকোডেড ডেলিভারি গাইড](ENCODED-DELIVERY.bn.md)।
